# THIRD PERSON BOXER 3D

「参照写真(グリッド地面の上でガードを構える3Dキャラクターを背後から
見下ろすカメラ)と同じ構図を、画像を背景に貼るのではなく、実際の3D
モデル・3D地面・3Dカメラで再現してほしい」という依頼から始まった
プロジェクトです。最初のバージョンではカメラ位置と空間構成のみを
再現し、続けて「左右スワイプで素早く回避移動する操作感を試したい」
という依頼でスワイプ操作(左右移動)を追加、さらに「回避時に姿勢も
変化させてほしい(上半身を傾け、腰を落とし、膝を曲げる、格闘ゲームの
ような紙一重の回避動作)」という依頼で回避姿勢のアニメーションを
追加しました。その後、別プロジェクト`humanoid-gltf-exporter`で
書き出したGLTF(.glb)の人型モデルを「試しに追加してみて」という依頼で
取り込み、キャラクターを素のプリミティブ構築からGLTFモデル読み込みへ
置き換えました。さらに、`humanoid-gltf-exporter`で作成したポーズ
アニメーションJSON(しゃがみ込みながら後方へ沈み込むポーズ)を
「実装して試してみてほしい」という依頼を受け、どう再生させたいかを
確認した上で「下スワイプで再生(左右の回避移動と同じジェスチャー方式で、
1回再生する)」という方針で、下スワイプによるしゃがみ込みアニメーション
として追加しました(詳細は後述「下スワイプでのしゃがみ込み
アニメーション」を参照)。続けて、`humanoid-gltf-exporter`で作成した
別のポーズアニメーションJSON(両腕を構えたボクシングのガードポーズ)を
「アイドル状態(常時構え)としてループ再生してほしい」という依頼で、
何も操作していないときに常時ループ再生される構えアニメーションとして
追加しました(詳細は後述「アイドル状態(常時構え)のループ再生」を参照)。
その後、Tripoで生成した新しいボクサーキャラクターのモデル(`.glb`)を
「このモデルを出してください」という依頼で受け取り、キャラクターモデルを
`humanoid.glb`からこの新モデル(`assets/boxer.glb`)へ差し替えました
(詳細・制約は後述「新モデル(`boxer.glb`)への差し替え」を参照)。

スマートフォン縦画面専用の試作です(PC操作は想定していません)。
攻撃・敵・HP・ダメージ・エフェクト・UI・サウンド・ゲームルールなど、
依頼されていない要素は追加していません(アニメーションは、アイドルの
構えループと下スワイプのしゃがみ込みの2本のみ、依頼を受けて追加して
います)。

Three.js製。キャラクターは、Tripoで生成したボクサーキャラクターの
静的メッシュ(`assets/boxer.glb`)を`GLTFLoader`で読み込んで表示して
います(以前は`humanoid-gltf-exporter`で書き出したリグ付きモデル
`assets/humanoid.glb`を使用していましたが、差し替えました。詳細は
後述「新モデル(`boxer.glb`)への差し替え」を参照。`humanoid.glb`自体は
参考用にリポジトリへ残しています)。タイトル・キャラクターデザインは
参照写真とは無関係の完全オリジナルです。

## 遊び方

`index.html` をブラウザで開くか、ローカルサーバーで配信してください。

```bash
cd games/third-person-boxer-3d
python3 -m http.server 8080
# http://localhost:8080 を開く(スマートフォンの縦画面を想定)
```

- **何も操作していないとき**: `humanoid-gltf-exporter`で作成した
  ボクシングのガードポーズ(両腕を構えた姿勢)が、継ぎ目なくループ
  再生され続ける(詳細は下記「アイドル状態(常時構え)のループ再生」を
  参照)
- **左スワイプ**: キャラクターが左へ素早く移動しながら、上半身を
  左へ大きく傾け、腰を落として膝を曲げ、パンチを紙一重で避けるような
  姿勢を取る。移動・姿勢とも一瞬で最大になったあと、起き上がり
  小法師のように素早くアイドルの構え姿勢へ戻る
- **右スワイプ**: 左スワイプと完全に左右反転した動作
- **左へ回避中に右スワイプ**(またはその逆): 新たに逆方向へ移動する
  のではなく、アイドル位置への復帰動作を通常より速くする
- **下スワイプ**: `humanoid-gltf-exporter`で作成したポーズアニメーション
  (しゃがみ込みながら後方へ沈み込む)を1回再生する。しゃがみきった
  あと、同じ速さで自動的にアイドルの構え姿勢へ戻る。再生中は左右
  スワイプを含む新しい入力を受け付けない(詳細は下記「下スワイプでの
  しゃがみ込みアニメーション」を参照)

## 仕組みメモ

### カメラ

参照写真は「頭が地平線のすぐ下に来て、キャラクターが画面下半分を
大きく占める、やや見下ろし気味の三人称視点」という構図だったため、
`computeCameraPose()`で以下のパラメータを調整して再現している。

- 視野角(FOV) 42度
- カメラ高さ 1.85(キャラクターの頭の高さよりやや上)
- カメラ距離 3.0(キャラクターの背後、Z軸プラス方向)
- 注視点の高さ 1.5(カメラよりやや低い位置を見ることで、緩やかな
  見下ろし角度をつけている)

キャラクターは原点に立たせ、`player.rotation.y = Math.PI`で180度
回転させることで背中をカメラ側に向けている。

### 地面のグリッド

当初はCanvasで描いたグリッド柄のテクスチャをタイル状に繰り返し
貼る方式を試みたが、非常に大きな単一平面上ではタイルの境界線が
期待通りに繰り返し表示されず(High-DPIで確認するとタイル自体は
正しく生成されているにもかかわらず、通常解像度では極端に見えにくい
という問題があった)、代わりに実際の3Dライン形状である
`THREE.GridHelper`を単色の地面メッシュの上に重ねる方式に変更した。
こちらは常に確実に描画される。

### キャラクター

現在は、Tripoで生成したボクサーキャラクターの静的メッシュ
(`assets/boxer.glb`、ボーン・スキンなし)を`GLTFLoader`で読み込んで
表示している。**このモデルにはボーンが1本も存在しないため、下記の
ボーン回転によるポーズ制御はすべて何もしない(`if (bones.spine)`等の
ガードで安全に無視される)**。回避・しゃがみ込みでキャラクター全体が
動いて見えるのは、ボーンの回転ではなく、後述の`player.position`(全体の
座標)が変化し続けているため。詳細な経緯は後述「新モデル
(`boxer.glb`)への差し替え」を参照。

以下は、ボーン付きモデル(`assets/humanoid.glb`)を使っていた当時の
仕組みの記録(コード自体は変更していないため、`humanoid.glb`相当の
ボーン付きモデルに差し替えれば、そのまま同じように機能する)。

`humanoid-gltf-exporter`で書き出した19ボーンの人型`SkinnedMesh`モデル
(`assets/humanoid.glb`)を`GLTFLoader`で読み込んで表示していた。

**注意点**: 書き出し元のページはアニメーション再生中に`.glb`を
エクスポートしたため、各ボーンの初期回転にアニメーション再生途中の
姿勢(腕を振っている最中の姿勢)がそのまま焼き込まれてしまっていた。
読み込み直後に`model.traverse()`で全ボーンの`quaternion`を
`identity()`にリセットし、回転のない直立のニュートラル姿勢から
始まるようにしている。

回避姿勢(後述)は、モデル内の同名ボーン(`Spine`/`LeftUpperLeg`/
`RightUpperLeg`/`LeftLowerLeg`/`RightLowerLeg`)を直接回転させることで
反映しており、以前のプリミティブ版にあった「肘を張り出したガードの
構え」は引き継いでいない(GLTFモデルの初期姿勢は腕を体側に下ろした
ニュートラル姿勢)。

接地シャドウは、動的なシャドウマップではなく、放射状グラデーションを
描いたCanvasテクスチャを地面に薄く重ねる「フェイクシャドウ」方式に
している(参照写真の柔らかい影の見た目に近いため)。シャドウは
キャラクターの左右移動に追従する。

### 左右スワイプでの回避移動

Three.js非依存の純粋関数として実装しているため、Node上でロジックだけを
単体テストできる。

- `classifySwipe(dx, dy, dt)`: ポインターの移動量・時間から左右
  スワイプを判定する(縦方向の移動が大きすぎる、移動量が小さすぎる、
  時間がかかりすぎている場合はスワイプと見なさない)
- `onSwipe(state, direction, now, currentX)`: スワイプ方向を受けて
  次の状態を返す。現在と逆方向への「ディフェンス中」の逆スワイプが
  来た場合は、ニュートラルへの復帰(`return`)を通常より短い
  duration(`FAST_RETURN_MS`)で即座に開始する。それ以外は目的方向
  (`DODGE_X`)へ向かう`out`フェーズを(再)開始する
- `advanceDodge(state, now)`: `out`フェーズの時間が経過したら自動的に
  `return`フェーズへ、`return`フェーズの時間が経過したらニュートラルの
  空状態へ遷移させる
- `computeDodgeX(state, now)`: 経過時間をイーズアウト(`easeOutCubic`)
  で補間し、現在のX座標を返す

毎フレーム`advanceDodge`→`computeDodgeX`の結果を`player.position.x`
(および接地シャドウの位置)に反映しているだけで、パンチや被弾などの
判定は一切持たない。

### 回避姿勢(上半身の傾き・腰落とし・膝の曲げ)

`computeDodgeX(state, now)`をそのまま`DODGE_X`で割ることで、
X移動と完全に同期した「回避の進行度」(`computeDodgeProgress`、
-1=左いっぱい〜0=ニュートラル〜+1=右いっぱい)を求め、これ1つを
入力に`computeDodgePosture(progress)`が以下の姿勢パラメータを返す
(すべてThree.js非依存の純粋関数)。

- `leanZ`: 上半身を回避方向へ傾ける角度。符号は`progress`と同じ
  (左回避なら負)
- `leanX`: 上半身を前へかがめる角度(パンチを潜り抜けるような前傾。
  左右どちらの回避でも同じ量だけ前傾する)
- `crouchDrop`: 腰を落とす量(キャラクター全体のY座標を下げる)
- `hipBend` / `kneeBend`: 股関節を前へ曲げる角度と、膝でその逆方向に
  大きめに曲げ返す角度。単純に脚を前に振り出すのではなく、膝から
  下だけ後ろへ戻すことで「足を大きく踏み出しすぎない、その場で
  重心を落とす」しゃがみ姿勢に近づけている

これらはすべて`|progress|`(回避の深さ)に比例するため、回避の
移動距離が最大になる瞬間(`out`フェーズ終了時、開始から140ms)に
姿勢も最も深くなり、`return`フェーズで移動と姿勢が同時に
ニュートラルへ戻る。

### 下スワイプでのしゃがみ込みアニメーション

左右の回避移動はコード側で姿勢を計算する手続き的なアニメーションだが、
これとは別に、`humanoid-gltf-exporter`で作成したポーズアニメーション
JSON(フレーム単位の`pose`(全ボーンの姿勢)と`modelPosition`(モデル
全体の絶対座標)のキーフレーム列)を再生する、もう一つの仕組みを追加した。

#### データはそのままゲームへ持ち込める形式

`humanoid-gltf-exporter`のキーフレームシステムは、最初から「将来ゲーム
制作で利用すること」を前提に設計されており(`pose`/`modelPosition`を
独立したフィールドとして保持し、`modelPosition`は絶対座標のまま保存する
など)、実際にこのアプリから書き出した3キーフレームのポーズアニメーション
JSONを、変換なしでそのまま`DUCK_CLIP`として埋め込んで再生できた。

```js
const DUCK_CLIP = {
  keyframes: [
    { time: 0,   pose: { Hips: [0,0,0,1], ... }, modelPosition: [0, 0, 0] },
    { time: 0.5, pose: { Hips: [...], LeftForearm: [...], ... }, modelPosition: [-0.03, -0.40, -0.41] },
    { time: 0.9, pose: { ... }, modelPosition: [-0.01, -0.40, -0.42] },
  ],
};
```

補間ロジック(`findBoundingKeyframes`・`sampleClip`)も、エディタ側の
`applyBonePoseAtTime`/`applyModelTransformAtTime`と同じ考え方をそのまま
移植している。POSEは球面線形補間(slerp)、MOVE(`modelPosition`)は
線形補間(lerp)でつなぐ。

#### 下スワイプ=「out→return」の一回再生

既存の左右回避移動と同じ「out(最大まで)→return(ニュートラルへ戻る)」
という状態機械の考え方を踏襲し、しゃがみ込みにも適用した。

- `out`フェーズ: クリップを`time=0`(直立)から`time=0.9`(しゃがみ
  きった姿勢)まで、クリップ本来のテンポ(0.9秒)で順方向に再生する
- `return`フェーズ: 同じクリップを`time=0.9`から`time=0`まで、同じ
  0.9秒かけて逆方向に再生する(クリップ自体を逆再生することで、専用の
  「戻りポーズ」を別途用意しなくても自然に元の直立姿勢へ戻れる)

下スワイプを検知すると`triggerDuck`で`out`を開始し、進行中の左右回避
(`dodgeState`)があれば打ち切る。しゃがみ込みの再生中(`out`・`return`
のいずれか)は、新しいスワイプ入力(左右・下とも)を一切受け付けない
(一連の「しゃがんで→戻る」動作を最後まで邪魔されずに再生し切るため)。

#### 既存の回避姿勢との排他制御

しゃがみ込みクリップは19本全ボーンの姿勢とモデル全体の位置を毎フレーム
丸ごと決めるため、レンダーループでは「しゃがみ込み再生中はクリップの
適用のみを行い、通常の回避姿勢の計算・適用は一切行わない」という完全な
排他制御にしている。しゃがみ込みが終わってニュートラルへ戻ると、
`Hips`・`LeftForearm`(回避姿勢では使っていないボーン)を明示的に
直立姿勢へリセットしてから、通常の回避姿勢の制御に戻す。

#### classifySwipeの拡張(下方向の検出)

既存の`classifySwipe`は「横方向の移動が縦方向より十分大きい場合」だけを
左右スワイプとみなしていた。これに「縦方向の移動が横方向より十分大きく、
かつ下向きの場合」という条件を追加し、下スワイプを検出できるようにした
(上方向のスワイプは今回のスコープに含まれないため未対応のまま)。

```js
if (ady >= SWIPE_THRESHOLD_PX && ady > adx * 1.2 && dy > 0) {
  return "down";
}
```

### アイドル状態(常時構え)のループ再生

下スワイプのしゃがみ込みに続けて、「何も操作していないときは、常に
ボクシングのガードポーズ(両腕を構えた姿勢)をループ再生させてほしい」
という依頼を受けた。これにより、以前は「回転なしの直立(T字に近い)
姿勢」だったデフォルト状態が、常時構えのループアニメーションに
置き換わっている。

#### 先頭と末尾が一致するクリップでシームレスにループする

しゃがみ込みと同じ仕組み(`sampleClip`によるPOSEのslerp・MOVEのlerp
補間)を再利用しつつ、`IDLE_CLIP`というもう1本のクリップを追加した。
このクリップは先頭(`time=0`)と末尾(`time=1.333...`秒)の`pose`・
`modelPosition`が完全に一致するように作られているため、単純に
「経過時間をクリップの長さで割った余り」を再生時刻として使うだけで、
継ぎ目(ポーズが一瞬飛ぶような違和感)なくループできる。

```js
function computeIdleClipTime(nowMs) {
  return (nowMs / 1000) % IDLE_LOOP_DURATION; // IDLE_LOOP_DURATION = クリップの長さ(秒)
}
```

#### 3状態(ダウン・ドジ・アイドル)の完全排他制御

レンダーループは、しゃがみ込み(ダウン)・左右の回避移動(ドジ)・
アイドルの構えループという3つの状態のうち、常にどれか1つだけが
その瞬間のボーン・モデル位置を完全に支配する構成にした(優先順位は
ダウン > ドジ > アイドル)。

```js
if (duckState.phase) {
  // しゃがみ込みクリップが支配する
} else if (dodgeState.phase) {
  // 既存の回避姿勢(手続き的なポーズ計算)が支配する
} else {
  // アイドルの構えループが支配する(ダウンもドジも行っていないとき、常に)
}
```

ドジ・ダウンのどちらも行っていない瞬間は必ずアイドルブランチに入るため、
「何も操作していないとき」は常にガードポーズのループ再生になる。逆に、
左右スワイプや下スワイプが始まった瞬間、アイドルループは即座に中断され、
それぞれの動作(回避姿勢・しゃがみ込みクリップ)がボーンを完全に
支配する。動作が終わってその動作自身の状態(`dodgeState`/`duckState`の
`phase`)がニュートラルに戻ると、次のフレームから自動的にアイドル
ループへ戻る。

#### 既存機能への影響・今回の簡略化点

- 左右の回避移動(`dodgeState`)・しゃがみ込み(`duckState`)の判定・
  状態遷移ロジック自体は一切変更していない。アイドルループは、
  その両方が「ニュートラル(phase: null)」のときにだけ再生される、
  いわば一番下のレイヤーとして追加しただけである
- 回避移動・しゃがみ込みのどちらも、開始した瞬間にアイドルのポーズから
  それぞれ自身のポーズ計算(回避姿勢、またはしゃがみ込みクリップの
  `time=0`)へ切り替わる。アイドルのポーズと回避/しゃがみ込みの開始
  ポーズを滑らかに繋ぐクロスフェード(ブレンド)は行っておらず、
  瞬間的な切り替えになる(依頼の範囲が「アイドルのループ再生」
  だったため、他の状態との補間までは今回のスコープに含めていない)
- 同様に、回避・しゃがみ込みが終わってアイドルへ戻る瞬間も、クロス
  フェードなしの瞬間的な切り替えになる

### ベンダーファイル

`vendor/three.module.min.js`と同じrevision(r160)の
`vendor/loaders/GLTFLoader.js`、およびそれが依存する
`vendor/utils/BufferGeometryUtils.js`を、`humanoid-gltf-exporter`と
同じ手順(npm経由で取得した`three@0.160.0`から配置)で追加した。

反映先は以下の通り(GLTFモデル内の同名ボーンを直接回転させている。
各ボーンがちょうど腰・股関節・膝の位置にあるため、追加のピボット
グループなしでそのまま支点として使える)。

- `Spine`ボーン(腰のすぐ上にあり、旧`upperBody`と同じ高さが支点に
  なる): `rotation.z`に`leanZ`、`rotation.x`に`leanX`
- `LeftUpperLeg`/`RightUpperLeg`ボーン(股関節の位置): `rotation.x`に
  `hipBend`(両脚とも同じ値、回避方向に関わらず対称に曲げる)
- `LeftLowerLeg`/`RightLowerLeg`ボーン(膝の位置): `rotation.x`に
  `kneeBend`
- `player.position.y`: `-crouchDrop`

モデルの読み込みは非同期のため、ボーン参照が揃うまでは
レンダーループ側で判定してスキップし、読み込み完了後から回避姿勢の
反映を開始する。

キャラクターは背中をカメラに向けて180度回転しているため、
「回避方向と同じ符号で上半身を傾けると画面上でも同じ方向に見える」
という向きの整合性は、実際に頭部のワールド座標を測定して検証済み。

### 新モデル(`boxer.glb`)への差し替え

Tripoで生成したボクサーキャラクター(スキン・テクスチャ済みの静的
メッシュ、ボーンなし)の`.glb`ファイルを受け取り、「このモデルを
出してください」という依頼で、このゲームのキャラクターとして表示する
よう差し替えました。

#### 新モデルには骨格がない

受け取ったモデルをバイナリ解析して調べたところ、メッシュ1個・
スキン0個・アニメーション0個の、完全な静的メッシュだった(Tripoの
無料プランではリグ(骨格)が付与されないため)。一方、既存の
`humanoid.glb`は19ボーンの`SkinnedMesh`で、回避・しゃがみ込みの
姿勢制御はすべて「モデル内の特定の名前のボーンを直接回転させる」
実装になっている。そのままモデルファイルだけを差し替えると、
ボーン参照(`model.getObjectByName("Spine")`等)がすべて`null`になる。

幸い、該当箇所はすべて`if (bones.spine) { ... }`のような形で防御的に
書かれていたため、差し替えただけではクラッシュはしない。しかし
「ボーンが見つからないので何もしない」が静かに起きるだけなので、
そのままでは回避・しゃがみ込み中も腕や脚が一切動かず、Tポーズ
(腕を真横に伸ばした姿勢)のまま固まって見えるという問題があった。

#### 試みたこと1: 既存スケルトンのスキンウェイト自動転写(不採用)

まず、`humanoid.glb`の19ボーンの骨格を新モデルにそのまま流用できない
か検討した。両モデルともほぼ同じ比率の人型キャラクターだったため、
新モデルの各頂点に対して「骨(ボーンの始点〜終点を結ぶ線分)までの
距離が近いボーンほど強く影響する」という単純な距離ベースの自動
ウェイト付け(直線距離、およびメッシュの辺をたどる測地距離の両方を
試した)で`SkinnedMesh`を構築し、`GLTFExporter`で新しい`.glb`として
書き出すスクリプトを作成した。

静止したバインドポーズでは正しく表示できたが、実際にゲームが使う
`IDLE_CLIP`(アイドルの構えポーズ)を適用すると、手足の一部の頂点が
正しいボーンではなく近くの無関係なボーン(胴体や反対の脚など)に
引っ張られ、グローブが首元でちぎれる・太もも付近に布が巻きついた
ように見えるなど、明らかな破綻が発生した。測地距離に変更しても
(アーム部分を一旦T字から下げ姿勢へ折り曲げる前処理を加えても)
改善せず、むしろ悪化するケースもあった。単純な距離ベースの
自動リグ生成では、このモデルの品質で実用に耐えるウェイトを
得られないと判断し、この案は不採用とした。

#### 試みたこと2: 静的メッシュに「気をつけ」姿勢を焼き込む(不採用)

スキニングを諦め、ボーンなしの静的メッシュのまま、T字の腕を
「体側に下ろした姿勢」へ一度だけ(ゲーム実行時ではなく、アセット
準備の段階で)折り曲げて焼き込む案も試した。肩を支点に腕の頂点群を
一括回転させる単純な処理だが、頂点をX座標で「腕」「胴体」と
二値分類して回転させると、分類の境界で接続された頂点同士が
引き裂かれて布のような尖った三角形(コウモリの羽根のような形状)に
伸びてしまった。滑らかな重み付け(smoothstep)に変更して伸びは
解消したものの、今度はこのキャラクターの腕が胴の高さに対して長い
比率のため、90度下げると手が腰の横ではなく短パンの側面に食い込んで
見えてしまい、不自然さが残った。角度を調整してもどちらかの問題が
再発したため、これも不採用とした。

#### 最終的な対応: モデルは無加工のまま差し替え、コード側は無改修

上記2案がいずれも視覚的な破綻を残したため、最終的には「見た目の
破綻なく確実に動く」ことを優先し、新モデルを**元のTポーズのまま**
(`humanoid.glb`と同じ高さ・接地位置に拡大縮小・平行移動しただけ)
`assets/boxer.glb`として配置し、`main.js`のモデル読み込みパスだけを
`./assets/humanoid.glb`から`./assets/boxer.glb`に変更した。ボーン
検索・回避姿勢・しゃがみ込みクリップのコードは一切変更していない
(前述の通り、ボーンが見つからない場合は安全に無視される設計に
なっているため)。

この結果、実際のゲーム内の見た目は以下のようになる。

- **常に腕を真横に伸ばしたTポーズで表示される**(個々の手足を
  曲げるポーズ制御がすべて無効なため)
- **アイドル中**: `IDLE_CLIP`の`modelPosition`(モデル全体の座標)
  トラックは引き続き適用されるため、キャラクター全体がごくわずかに
  揺れ続ける(ポーズそのものは変化しない)
- **しゃがみ込み(下スワイプ)**: `DUCK_CLIP`の`modelPosition`により、
  キャラクター全体が沈み込んで戻ってくる動きは見える(手足は曲がらない)
- **左右の回避(スワイプ)**: `dodgeState`による`player.position`の
  左右移動・`crouchDrop`による上下移動はボーンを使わないため、
  そのまま機能する(上半身の傾き・膝の曲げだけが効かない)

個々の手足が曲がらない点は明確な制約だが、キャラクター自体が
左右移動・沈み込みに応じて確実に動き、見た目が破綻(テアリングや
めり込み)することもない。モデルに骨格を与えて本来の滑らかな
アニメーションを取り戻すには、Blenderでの自動ウェイト付けや、
Tripoの有料プランでのリグ出力など、このリポジトリのスクリプトでは
行っていない作業が別途必要になる。

## 相手(USAボクサー)の攻撃遷移テスト(Idle → 左ジャブ → Idle)

AIやゲームロジックから攻撃アニメーションへ遷移できるかを確かめるため、相手のUSAボクサーが
**5〜10秒のランダムな間隔で左ジャブを繰り返す**ようにした。ダメージ判定・プレイヤーへの追従・
戦闘判断はまだ作っていない(遷移のループが正しく動くことの確認だけ)。

```
Idle ──(5〜10秒のランダム待機)──▶ 左ジャブ ──(最後まで再生)──▶ Idle ──(また5〜10秒)──▶ 左ジャブ …
```

- **待機時間**: 「次の攻撃を始めるまで」の時間として、Idleに入るたびに5〜10秒から決め直す
  (`pickEnemyWaitMs`)
- **ジャブ中はタイマーを作らない**: ジャブが最後まで再生されてIdleへ戻った**その時点から**、
  次の5〜10秒を数え始める(`advanceEnemy`が`jab`→`idle`の遷移でだけ`createEnemyState`を呼ぶ)。
  左ジャブ終了後は必ずIdleへ戻る
- **状態機械は純粋関数**(`createEnemyState`/`advanceEnemy`。時刻と乱数を引数で受け取る)。
  描画ループでは`stepEnemyState`が毎フレーム呼び、状態が変わったときだけログを出す
- **アニメーション**: Idle(`assets/fightIdleUsa.json`)は常に再生し続け、ジャブ中だけ
  ジャブ(`assets/leftPunchUsa1.json`。humanoid-gltf-exporterで作ったUSAボクサーの左ジャブ)を
  上に重ねる。ジャブの頭の0.12秒と終わりの0.15秒は、Idleの姿勢と混ぜて(クォータニオンのslerp)
  なじませるので、遷移で姿勢が飛ばない。ジャブの長さは、**クリップの最後のキーフレームの時刻
  (1.0秒)**を使う(JSONの`totalFrames`は60=2秒だが、キーフレームは30フレームで終わるため)
- **既存のシステムは変更していない**: 既存のクリップ再生(`sampleClip`)・モデル・スケルトン・
  プレイヤーの動きはそのまま。相手の更新関数`updateOpponentIdle`を、同じ処理にジャブの重ねを足した
  `updateOpponent`へ置き換えただけ

- **状態機械(擬似の時計で、10000回の攻撃)**: 待機時間は5.001〜10.000秒(平均7.49秒)の範囲に収まり、
  Idleからしかジャブにならず、ジャブは必ず最後(1.0秒)まで再生されてからIdleへ戻り、
  ジャブ中に新しいタイマーが作られることはなかった(違反0件)。乱数を固定すると、例のとおり
  7.3秒→ジャブ→5.8秒→ジャブ→9.1秒の順になる
- **実機のブラウザで通しの動作**(約26秒、3回のジャブ): 開始0.3秒で`Idle`と`Next attack in 5.9s`、
  6.2秒に`Left Jab`、1.0〜1.1秒後に`Return to Idle`、続けて`Next attack in 7.7s`、実際にその7.7秒後に
  次のジャブ、…と、予告した待機時間(5.9・7.7・9.3・8.9秒)どおりに攻撃した。相手の左手の位置は、
  Idle中はずっと−1.38〜−1.36で動かず、ジャブ中だけ−0.997まで約0.37m前(プレイヤー側)へ伸び、
  ジャブのあとはIdleの位置へ戻った。コンソールのエラーなし
- 動作の確認用に、`window.__enemy`(`getState`/`getLog`/`advanceEnemy`など)を公開している

## パンチが届く距離まで2人を近づけた

左ジャブの拳が実際にプレイヤーに届く距離まで、2人を近づけた(以前は約1.7m離れていて、
ジャブの拳はプレイヤーの手前約0.9mで止まっていた)。

- **ジャブの届く長さを実測**: `leftPunchUsa1.json`の全キーフレームで相手の左手首のワールド位置を
  調べると、インパクト(7フレーム)で、相手の基準位置から**前へ約0.73m**(体の前進0.12mを含む)、
  高さ1.28m、横は左へ+0.12m伸びる。拳はそこからさらに約0.13m先まで出る
- **配置**: プレイヤーの顔の前に拳が届くよう、相手を`OPPONENT_BASE`=(−0.12, 0, −1.0)に置いた
  (プレイヤーの頭は(0.01, 1.28, −0.03))。相手の左手は+X側に伸びるので、その分(−0.12)左へずらした
- **カメラ**: 相手が近づくと画面上で大きくなり、プレイヤーの後ろに隠れやすくなるため、距離と高さを
  再計算した(`CAMERA_HEIGHT`=2.7、`CAMERA_DISTANCE`=1.7、`LOOK_AT_HEIGHT`=1.68)。頭頂が画面の約46%
  (プレイヤー)・約24%(相手)になり、相手がプレイヤーの約6割の大きさで見える(以前は約半分)。
  縦長・横長のどちらの画面でも、2人とも映る
- **確認**: ジャブのインパクト(開始から約0.24秒)で、相手の左手首が(0.02, 1.28, −0.32)、
  プレイヤーの頭が(0.01, 1.28, −0.03)で、手首は頭の中心から0.30m(頭の前面の直前)、胸から0.41m。
  拳(手首の先約0.13m)がプレイヤーの顔の前面に届く。Idle→ジャブ→Idleの遷移のログ・
  5〜10秒の待機は、前回から変わらず動く。コンソールのエラーなし
- ダメージ判定は引き続き作っていない。プレイヤーが左右の回避(スワイプ)で動くと、拳は空を切る

## 敵とプレイヤーの中心線(X軸)を合わせた

前後(Z軸)の距離はそのままで、敵だけを左右(X軸)に動かして、プレイヤーと同じX座標(画面中央)に
合わせた。`OPPONENT_BASE`のxを−0.12→0にした(z=−1.0、y=0は変更なし)。カメラは変更していない。

- 以前は、ジャブの拳がプレイヤーの顔の正面に届くよう、敵を−0.12だけ左へずらしていた。
  中心線を合わせると、ジャブ(相手の左手が+X側へ約0.12m寄って伸びる)は、プレイヤーの顔の
  中心ではなく、少し+X側(プレイヤーの頭の横〜肩)へ向かう
- 確認(Idleを1.5秒間、0.1秒ごとに記録した平均): プレイヤーの基準x=0.001・Hips x=0.001・
  Chest x=0.004・Head x=0.012、敵の基準x=0・Hips x=0.000・Chest x=−0.006・Head x=−0.015で、
  両者の中心線は一致している(差は2cm未満。Idleのわずかな左右の揺れによる)。Zは敵が−1.0のまま、
  プレイヤーが約0のままで、奥行きは変わっていない

## スリング式の左ジャブ(左肩タップ)のプロトタイプ

Sling Kongのような「ゴムを弾く」感覚のパンチ入力の操作感を確かめるための、最小のプロトタイプ。
**プレイヤーの左肩付近をタップすると、左ジャブが1回出る**。右パンチ・フック・アッパー・スワイプでの
方向指定・攻撃判定・ダメージ・敵AIとの連動・コンボ・引っ張り量による威力変化は作っていない。

### 入力
- **タップ判定**: プレイヤーの左肩(左上腕の付け根のボーン)を画面に投影した位置を中心に、
  半径0.17m(`JAB_HIT_RADIUS_M`。画面上で約80px。最小44px)の円。肩のボーンに追従するので、
  回避で動いたり構えが揺れたりしても、肩の位置についてくる。プレイヤーは背中をカメラに向けて
  いるので、モデルの「左」は画面の左側に見える。体の中央や右側をタップしても出ない
  (最初に半径0.3mにしたところ、体の中央まで入ってしまったので0.17mに絞った)
- **タップの瞬間に出す**: 指を離すのを待たず、`pointerdown`で発動する(離すまで待つと、その分だけ
  拳が出るのが遅れて「パッと弾ける」感じが弱くなる)。トレードオフとして、**左肩から始まった
  スワイプは、回避ではなくジャブとして扱う**(肩の円の外から始めたスワイプ・しゃがみ込みは従来どおり)
- 1タップ=1回の左ジャブ。位置による方向の指定はない
- `?debug=1`を付けて開くと、タップ判定の円を半透明の赤で表示する(動作確認用)

### 使うモーション
すでにある`humanoid-gltf-exporter`製の、ボクサー用「踏み込んで左ジャブ」
(`assets/leftPunch1.json`。腰を沈めて左足を踏み出しながら打ち、後ろ足を引き付けて元の位置へ戻る)を
**そのまま**使う。新しいモーションは作っていないし、ファイルも変更していない。

- 当初は、その場で打つ版(`leftPunch.json`)を使ったが、ジャブの拳が約0.25mしか伸びず(手首が
  z=−0.30→−0.55)、1m先にいる相手の手前で止まってしまったため、踏み込む版に切り替えた。
  踏み込む版は約0.38m伸びる(手首がz=−0.70。拳はその先約0.13m)ので、相手の目の前まで届く
- クリップはモデル向き(+Z)で作られている。プレイヤーはY軸で180°回っているので、クリップの
  `modelPosition`(体の前進・沈み込み)は、xとzの符号を反転してワールドへ適用する
- 再生は、クリップの先頭から「構えに戻った時点」(43フレーム=約1.43秒)まで。末尾の、
  構えのまま止まっている区間(43〜60フレーム)は使わない(`findJabActiveRange`。キーフレームは
  変更せず、再生する範囲を決めるだけ)

### 遷移(状態機械)
```
IDLE ──(左肩タップ)──▶ LEFT_JAB ──(モーション終了)──▶ IDLE
```
- **多重再生の防止**: ジャブの再生中のタップは無視する(`tryLeftJab`が`[Player] Left Jab input ignored`を
  ログに出して戻る)。しゃがみ込み・回避の最中も、ジャブは始まらない。逆に、ジャブ中は回避・しゃがみ込みの
  スワイプも受け付けない(すでにあったしゃがみ込み中の排他と同じ考え方)
- **必ずIDLEへ戻る**: ジャブの長さが過ぎたら`advanceJab`が状態を初期化し、`[Player] Return to Idle`を出す。
  IDLEのクリップはジャブ中も止めずに進め続けるので、戻ったときに構えが飛ばない
- **なじませ**: ジャブの頭の0.06秒と終わりの0.15秒は、IDLEの姿勢・位置と混ぜる(姿勢はslerp、位置はlerp)
- 状態機械は、時刻を引数で受け取る純粋関数(`createJabState`/`triggerJab`/`advanceJab`)

### 調整用のつまみ(コードの先頭の定数)
今回は「既存モーションをそのまま再生して、スリング入力との相性を見る」ため、すべて素のまま:

| 定数 | 今の値 | 用途 |
|---|---|---|
| `JAB_SPEED` | 1.0 | 再生速度の倍率。大きくすると、より速く弾ける |
| `JAB_BLEND_IN_MS` | 60 | IDLEからジャブの姿勢へなじませる時間。短いほど弾ける感じ |
| `JAB_BLEND_OUT_MS` | 150 | ジャブからIDLEへ戻すなじませの時間 |
| `JAB_HIT_RADIUS_M` / `JAB_HIT_MIN_RADIUS_PX` | 0.17 / 44 | 左肩のタップ判定の大きさ |

発動直前の予備動作(ため)・ヒット時の演出は、まだ入れていない。

### 実測した値(ブラウザ、390×844の画面)
- タップから、拳が動き出すまで: **約50ms**(最初のフレーム。指を離すのを待たない)
- 拳が最も前へ出る(インパクト): **タップから約0.4〜0.5秒後**、手首が構えの位置から0.38m前
- モーション全体: 約1.43秒で構えに戻る
- **体感について**: 動き出しは即座だが、このクリップは腰を沈める「ため」の5フレーム(約0.17秒)を
  経て打つので、インパクトまで約0.4秒かかる。「パッ」とした弾け感が足りない場合は、`JAB_SPEED`を
  1.5前後にすると、インパクトが約0.25秒、全体が約0.95秒になる
- 左肩以外(体の中央・右側)のタップでは出ない。連打(再生中に30回、10ms間隔)でも、始まるのは
  1回だけで、ほかは無視される(ログのとおり、`Left Jab`の次は必ず`Return to Idle`が来てから次の`Left Jab`)。
  ジャブ終了後はIDLEへ戻り、手の位置も構えへ戻る。再度タップすると、もう一度出る。コンソールのエラーなし
- デバッグログ: `[Player] Left Jab` / `[Player] Left Jab input ignored (jab in progress)` /
  `[Player] Return to Idle`。`window.__jab`(`getState`/`getStats`/`tryLeftJab`など)で状態も取れる

## 下スワイプのしゃがみ込みを廃止/スリングのテスト終了/右肩タップで右ストレート

### 変更点
- **下スワイプ(しゃがみ込み)を廃止**: 今後の攻撃操作と競合するおそれがあるため、しゃがみ込みの
  クリップ・状態機械・入力・テスト用フック(`window.__duck`)をすべて取り除いた。縦方向の
  スワイプは、何も起こさない(`classifySwipe`は`null`)。左右スワイプでの回避は、そのまま残している
- **スリング式のテストは終了**: 「引っ張って弾く」感覚の検証は一区切りにして、今は肩付近を
  タップするだけでパンチが出る形にした(`PUNCH_SPEED`などの調整用の定数は残してある)
- **右肩をタップ → 右ストレート**(左肩をタップ → 左ジャブは、これまでどおり)

### 肩タップのパンチ
| タップ | パンチ | モーション | 長さ |
|---|---|---|---|
| 左肩 | 左ジャブ | `assets/leftPunch1.json`(踏み込む左ジャブ) | 約1.43秒 |
| 右肩 | 右ストレート | `assets/rightStraight.json`(新規。5キーフレーム) | 約0.6秒 |

- 左右の肩の円(半径0.17m、画面上で約80〜86px)は重ならない。`?debug=1`を付けると両方を赤い円で表示する
- **多重再生の防止**: パンチの再生中は、左右どちらの肩のタップも無視する(`[Player] Right Straight input ignored
  (Left Jab in progress)`のようにログに出る)。回避の最中も出ない。パンチ終了後は必ずIDLEへ戻る
- 状態は`punchState`(`null`=IDLE / `"leftJab"` / `"rightStraight"`)の1つだけで、純粋関数
  (`createPunchState`/`triggerPunch`/`advancePunch`)。コードは左右で共通(`PUNCHES`の表に
  クリップのURLと、タップ判定に使う肩のボーンを持つ)
- モーションは、ファイルを変更せず、クリップの先頭から「構えに戻った時点」まで再生する。
  プレイヤーが背中を向けている(Y軸で180°回っている)ため、`modelPosition`のxとzは符号を反転して適用する
- テスト用フックは`window.__jab`→`window.__punch`に変わった(`getState`/`getStats`/`tryPunch`/
  `shoulderScreenZone(kind)`/`punchAtScreen`など)

### 右ストレートのモーション(`assets/rightStraight.json`)
**ユーザー提供のモーション**(humanoid-gltf-exporterで調整した`rightStraight.json`)に差し替えた
(最初に私が作った5キーフレームの版は、置き換えて残していない)。キーフレームは8個(0・5・8・11・13・14・15・20フレーム、
30fps)で、最後(20フレーム)の姿勢は最初(0フレーム)と同じ。

- 再生する範囲は、先頭の構えから、構えに戻った20フレームまで(約0.67秒)。ファイルには
  `totalFrames: 60`(2秒)と書かれているが、キーフレームは20フレームで終わっているため、
  再生の長さにはキーフレームの最後の時刻を使う(`findPunchActiveRange`)。ファイルは変更していない
- 実測(ブラウザ、390×844): タップから約51msで動き出し、約0.4秒で右手が最も前へ出る
  (手首のz=−0.61。構えの−0.23から約0.38m前)。約0.64秒で構えに戻り、手の位置も構えへ戻る
- 連打(再生中に20回)や、左ジャブとの切り替え・多重再生の防止は、前のモーションのときと同じ
  ように動く(再生中のタップは無視。終わったら必ずIDLEへ戻る)

## プレイヤーの被ダメージ(敵のジャブが当たったらHPが減る)

「敵に殴られたら、本当にHPが減る」ことだけを実装した。プレイヤーの攻撃・スリング式の左ジャブ(肩タップ)・
敵の攻撃パターン(5〜10秒ごとの左ジャブ)・敵のやられモーション・試合時間・勝敗判定・コンボ・
ガード・UIのデザインは変更していない。

### しくみ
```
敵の左ジャブ ──▶ 拳がプレイヤーの頭か胸に重なった? ──はい──▶ プレイヤーHP −10 ──▶ 被弾状態
                                            └─いいえ(ジャブが終わるまで)──▶ Miss(ダメージなし)
```
- **HP**: これまでHPのしくみは無かったので新しく作った。`PLAYER_MAX_HP`=100、敵のジャブ1回=`ENEMY_JAB_DAMAGE`
  =10(テスト用の一定値。バランス調整はしていない)。画面の左上に`HP 100 / 100`と小さく表示する
- **当たり判定**: 敵の拳(左手首から、前腕→手首の向きへ0.12m先を中心とした半径0.10mの球)が、
  プレイヤーの頭(半径0.18m)・胸(半径0.24m)の球に重なったら命中。ジャブが伸びている間
  (開始から0.10〜0.36秒。拳が伸びきるのは約0.23秒)に毎フレーム調べる。姿勢を反映した直後の
  実際のボーンの位置を使うので、プレイヤーが回避で横へ動いたり、パンチで前へ出たりすると、
  それが判定に反映される。**1回のジャブでダメージを受けるのは最大1回**(当たった時点でそのジャブの判定は終わり)
- **Miss**: 判定の間に重ならず、ジャブが終わったら`Miss (no damage)`とログに出し、HPは減らさない
- **被弾状態**: ダメージを受けた瞬間から0.4秒間(`isPlayerHit`)。**被弾モーションはまだ無いため、
  新しく作っていない**。HPが減ることと、状態のフラグ、ログ、HP表示が赤く点滅することだけ
- **HPが0以下**: `playerKO`が`true`になり、`[Combat] Player HP is 0 (KO detected)`とログに出る。
  HPは0で止まり(マイナスにならない)、以降は減らない。KO演出・試合終了・勝敗判定は未実装

### ログ
`[Combat] Enemy Left Jab: HIT Head (-10) Player HP 90/100` / `[Combat] Enemy Left Jab: MISS (no damage)
Player HP 100/100` / `[Combat] Player HP is 0 (KO detected)`。`window.__combat`(`getHp`/`isKO`/`isHit`/
`getLog`/`setHp`/`applyDamage`/`forceEnemyJab`/`postponeEnemy`など)でも確認・操作できる
(`forceEnemyJab`は、ランダムな待機を待たずに敵のジャブを今すぐ出す、テスト用)。

### 確認結果(ブラウザ、390×844)
| 条件 | 結果 |
|---|---|
| 構えのまま(回避なし)でジャブを受ける(2回) | HIT(拳と頭の距離0.16〜0.17m)、HP 100→90 |
| 左へ回避(ジャブの開始と同時〜0.12秒後) | **MISS**(最短の距離0.33〜0.39m)、HP変わらず |
| 左へ回避(0.2秒後。拳がもう届く時刻) | HIT(回避が遅い)、HP 90 |
| 右へ回避(0.12秒後) | **MISS**、HP変わらず |
| 右へ回避(開始と同時・0.06秒後) | HIT。回避が早すぎて、拳が伸びきっている間(約0.23〜0.36秒)に |
| | プレイヤーが中央へ戻り、拳の位置(敵の左手は画面右寄り)を通るため |
- つまり、**拳が届く瞬間(約0.2〜0.3秒)に横へ外れていれば、ダメージを受けない**。早すぎる回避・遅すぎる回避は当たる。
  敵の拳は画面の右寄り(+X側)から来るので、左へ避けるほうが余裕がある(右は拳の通り道を通って戻る)
- 被弾状態は、命中の直後に`true`・HP表示は赤になり、約0.4秒後に戻る
- HP30から10ダメージを5回: 20→10→0(KO検出)→0→0。0のまま減らない
- **既存の動作**: 実際の敵の攻撃(5〜10秒のランダム待機)で、`[Enemy] Left Jab`のあと
  `[Combat] ... HIT`が出てHPが100→90→80と減る。プレイヤーの左肩・右肩タップのパンチは、
  これまでどおり出る(2回とも開始・終了)。コンソールのエラーなし

## パンチ入力をグローブタップへ変更 / 敵ジャブの予備動作

### 入力
- 左グローブ付近をタップ → 左ジャブ、右グローブ付近をタップ → 右ストレート（肩タップは廃止）。
- 判定円は毎フレーム、グローブ(手ボーン)のスクリーン座標に追従（`?debug=1` で赤円表示）。
- タップ/スワイプの分離: 押下位置にグローブがあり、移動 ≤14px かつ ≤350ms で離した場合のみパンチ（pointerup で確定）。
  それ以外の左右スワイプはグローブ上から始めても従来どおり「かわし」。長押しは何も起きない。
- パンチ中・かわし中の入力は無視（多重再生なし）。

### 敵(USA)左ジャブ
- `assets/leftJabWindupUsa.json`（4キー・0.53秒）: 左腕を高く大きく振りかぶり上体を傾けて「タメ」→ 高速ストライク(`ENEMY_STRIKE_MS=70`) → 既存ジャブの戻り → ガード。
- 当たり判定はストライク基準(+40〜130ms)。かわし中は無敵で `MISS (dodged)`。
- 5〜10秒のランダム待機は攻撃終了後に開始（従来どおり）。

### テスト結果 (Playwright)

## FATIGUE（疲労）ゲージ（プレイヤーのみ）
- 自分のパンチを**敵にガードされる**（+`FATIGUE_ON_GUARDED`=20）／**敵のパンチを喰らう**（+`FATIGUE_ON_HIT`=20）と、疲労ゲージがたまる（満タン `FATIGUE_MAX`=100 → 5回）。無条件ヒット（ノーガード中）はたまらない。かわし成功・敵に当てたときは増減なし。
- 満タンで**疲労状態**（`FATIGUE_MS`=4秒）。**左右スワイプのかわし以外、何もできない**（スリング開始・パンチ入力は無視。パンチ中・ノーガード中なら中断）。ゲージは疲労状態の間に満タンから0へ減っていき、0に戻ると解除。
- 疲労状態の間、**敵の攻撃頻度は倍**（待機2〜4秒 → 1〜2秒。開始時、待機中なら残り時間も半分）。**かわしに成功しても敵のガードは下がらない**（ノーガードのチャンスなし）。
- 見た目: 腕がだらんと下まで下がり、背中が丸まって頭が下がる。**体が赤く点滅**（マテリアルの発光）。効果音（力が抜ける下降音）。
- HUD: HPの下に「FATIGUE」ゲージ（黄→赤）。疲労中は赤く点滅し「疲労! 避けるしかできない」と表示。
- テスト: ガードされるたびに +20（20→100）／100で疲労状態・敵待機スケール0.5／疲労中スリング・パンチは無視、かわしはできる／疲労中のかわしでノーガードにならない／4秒後にゲージ0・スケール1に戻る／既存のテスト変化なし、エラーなし。
- 疲労ゲージは、疲労状態でないときは時間で減らない（仕様に無かったため）。必要なら自然回復を追加できる。

## 体力ゲージ・勝敗・敵の右ストレート・疲労の調整
- **体力ゲージ**: プレイヤー・敵とも体力100（`PLAYER_MAX_HP` / `ENEMY_MAX_HP`）。画面にはゲージだけ表示（数字は非表示、内部では動いている）。左=プレイヤー、右=敵（右から減る）。緑→黄→赤、被弾の瞬間は白く光る。

- **勝敗**: どちらかの体力が0になったら、その場で勝敗が決まる（`YOU WIN!` / `YOU LOSE` と「もう一度」ボタン）。以降、敵は新しい攻撃をせず、プレイヤーの操作も受け付けない（3カウント制は後で）。
- **敵の右ストレート**: 敵の攻撃は左ジャブ(60%)と右ストレート(40%)のランダム（`ENEMY_RIGHT_STRAIGHT_RATE`）。左ジャブと同じ「大きな予備動作→タメ→高速パンチ→戻り」で、予備動作は約0.7秒（右腕を大きく外へ引き、上体をひねる。`assets/rightStraightWindupUsa.json`）。パンチと戻りは `assets/rightStraight.json`（プレイヤーのものと同じクリップ）を再生。ダメージ判定・かわし・ノーガード・ガードのしくみは左ジャブと共通。
- **疲労の調整**: 疲労状態の長さ（回復）を1.2倍遅く: 4秒 → **4.8秒**（`FATIGUE_MS`）。疲労中の敵の攻撃頻度を今の1.5倍: 待機時間 ×0.5 → ×1/3（待機0.67〜1.33秒＝通常の3倍の頻度。`FATIGUE_ENEMY_WAIT_SCALE`）。
- テスト: 左ジャブ→敵HP-10／右ストレート→-15／敵の左ジャブ→プレイヤー-10／右ストレート→-15／敵HP0でWIN・以降の操作と敵の攻撃が止まる／疲労4.8秒・待機0.67〜1.33秒／既存テスト変化なし、エラーなし。

## 体力ゲージの表示（PLAYER / ENEMY）と、疲労中のかわしの暴走を修正
- 体力ゲージを左右に分け、ゲージの上に名前を表示: 左半分 = **PLAYER**、右半分 = **ENEMY**（敵のゲージは右から減る）。疲労ゲージはPLAYERのゲージの下。
- **疲労中にかわすとモーションが暴走する不具合を修正**: かわし中は、かわしが触らないボーン（腕・頭など）を毎フレーム書き直していなかったため、疲労の姿勢（腕を下げる）や被弾のけぞりなどの「上乗せ」が毎フレーム積み重なっていた。かわしの最初に、アイドルの構えを全ボーンに書き直すようにした（被弾中・スリング中のかわしでも同様に安定）。
