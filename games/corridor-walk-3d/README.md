# Corridor Walk 3D

初代バイオハザードのような「1枚の固定背景(プリレンダー背景)の上を、3Dキャラクターが
自由に動き回る」表現のプロトタイプです。実際に撮影した廊下の写真を背景として使い、
その上にThree.js製の簡易な人型キャラクター(5〜6頭身)をラジコン操作(タンク操作)で
歩かせられます。

## 遊び方

`index.html` をブラウザで開くか、ローカルサーバーで配信してください。

```bash
cd games/corridor-walk-3d
python3 -m http.server 8080
# http://localhost:8080 を開く
```

- 画面をドラッグすると、その場に仮想スティックが表示される
- **左右にドラッグ**でキャラクターが旋回
- **上にドラッグ**で前進、**下にドラッグ**で後進(ドラッグ量に応じて速度が変わる、
  ラジコン操作)
- 指を離すと停止
- 「リセット」で開始位置に戻る

## 仕組み: 本物の3D空間ではなく「写真+射影変換」で実現している

ご相談いただいた通り、1枚の写真からは本物の部屋の立体構造(奥行き)は分からないため、
実際のカメラ位置を復元して3D空間を作る、というアプローチは取っていません。
代わりに、初代バイオハザードの「固定背景+その上に3Dキャラを重ねる」という
古典的な手法を、次のように簡略化して再現しています。

1. 写真の中の「歩ける床」を、手動で4点(近い側の左右2点、奥側の左右2点)を
   指定して台形(クアッド)として定義する(`main.js`の`FLOOR_QUAD_IMAGE`)
2. その4点を「単位正方形→任意の四角形」の射影変換(homography)に変換する
   (`floorMap.js`の`computeQuadHomography`。テクスチャマッピングで使われる
   古典的なHeckbertの手法と同じもの)
3. キャラクターの位置を、写真とは無関係な抽象的な「床座標」(u, v。
   v=0が手前、v=1が奥)として管理し、射影変換でスクリーン座標に変換して
   表示する
4. キャラクターの表示スケールも同じ射影変換から導出する(奥に行くほど
   近傍点同士の画面上の距離が縮む=遠近感に応じて自動的に小さく表示される)
5. キャラクター自身はThree.jsの本物の3Dモデル(向きに応じて実際に回転する)
   だが、描画にはオルソグラフィックカメラを使い、位置とスケールは上記の
   射影変換で直接指定する。これにより「本物のカメラの視点計算」をせずに、
   写真の特定の遠近感に対して見た目を直接キャリブレーションできる

この方式のため、キャラクターは指定した床の四角形の中だけを歩けます
(棚や壁の裏に隠れる、家具にぶつかる、といった実際の当たり判定はありません)。

## 今回使用した写真とキャリブレーション

`assets/room.jpg` は、いただいた廊下の写真をEXIFの回転情報に従って正しい向きに
補正し、スマートフォン縦画面に近いアスペクト比(0.55)にトリミングしたものです。
背景`<img>`は`object-fit: cover`で画面いっぱいに表示されるため、実機の画面比率が
`assets/room.jpg`と異なる場合は表示時に上下または左右がさらにトリミングされます。
`floorMap.js`の`imageFractionToViewportFraction`がその分を補正し、画面比率が
違っても床の四角形とキャラクターの位置がずれないようにしています。

床の四角形(`FLOOR_QUAD_IMAGE`)は、写真を見ながら手動で座標を決めた簡易的な
キャリブレーションです。別の写真を使う場合は、この4点を撮り直した写真に合わせて
調整する必要があります。

## 仕組みメモ

- 判定・変換ロジックは`floorMap.js`にDOM/Three.js非依存の純粋関数として
  まとめている(Node上で直接ユニットテスト可能)
  - `computeQuadHomography` / `mapUnitToQuad` — 単位正方形から任意の四角形への
    射影変換(Heckbertの手法)
  - `computeLocalScale` — 射影変換から一貫した奥行きスケールを算出
  - `computeScreenForwardAngle` — 抽象的な「向き(heading)」を、現在の位置での
    画面上の実際の向きに変換(キャラクターが常に「歩いている方向」を向くように
    見せるため)
  - `imageFractionToViewportFraction` — `object-fit: cover`によるトリミング分の補正
  - `computeJoystickAxes` — タッチ開始位置からのドラッグ量を旋回/前後進の
    2軸に変換する仮想スティック入力
  - `computeCharacterStep` — 旋回・前後進の入力から次のフレームの
    位置・向きを計算する純粋関数
- キャラクターは頭・首・胴体・腕・脚をプリミティブ形状(球・カプセル・箱)で
  組んだプレースホルダーの人型モデル(頭部1ユニットに対して全身5.5ユニット)。
  移動中は腰(脚)・肩(腕)を支点にサイン波で振ってウォークサイクルを表現している
- 描画はオルソグラフィックカメラを使用し、キャラクターの位置・スケール・向きは
  すべて上記の射影変換から直接計算している(カメラの位置・回転・FOVを
  作り込んでキャリブレーションする必要がない)

## テスト

- `floorMap.js`の純粋関数をNode上で直接ユニットテスト(射影変換の4隅の対応・
  遠近スケールの単調減少・object-fit:coverの補正・ジョイスティック入力・
  キャラクター移動の境界クランプなど)
- Playwrightで実際に画像を読み込ませ、床の四角形内の複数地点にキャラクターを
  配置してスクリーンショットで写真上の床と視覚的に整合していることを確認
- 実ポインタドラッグでの前進/後進/旋回、指を離した際の停止、リセットボタンの
  動作を検証
- 4方向へのドラッグ操作を繰り返す長時間プレイを想定したストレステストで、
  位置・向きが常に有効な範囲に収まり続けることとエラーが出ないことを確認
- `window.__debug`フックは最終コミット前に削除済み

## スコープ外(意図的に未実装)

- 本物のカメラ姿勢の推定・複数写真からの3D復元(1枚の写真からは原理的に
  不可能なため、上記の射影変換による簡易的な表現にとどめている)
- 家具・壁との当たり判定(床の四角形の外に出られないだけで、四角形の中に
  家具があっても素通りする)
- 複数の部屋・カメラ切り替え(本家のような部屋ごとの固定カメラ切り替えは
  今回は1枚の写真のみのプロトタイプ)
