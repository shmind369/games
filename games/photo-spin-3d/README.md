# PHOTO SPIN 3D

1枚の写真を読み込むと、被写体を背景から切り出し、その輪郭(シルエット)に
沿って丸みのある立体形状を推測し、指でドラッグして360度グルグル回して
見られる疑似3Dビューアです。Three.js製。

## 遊び方(使い方)

`index.html` をブラウザで開くか、ローカルサーバーで配信してください。

```bash
cd games/photo-spin-3d
python3 -m http.server 8080
# http://localhost:8080 を開く
```

- 「画像を選ぶ」で好きな写真を読み込む
- **左右ドラッグ**で被写体を左右に回転、**上下ドラッグ**で上下に視点変更
- **ピンチ操作**で拡大・縮小
- 「リセット」で回転・ズームを初期状態に戻す

## v2: 「板を変形させるだけ」から「輪郭で背景を除去した立体形状」へ

初期バージョンは1枚の平面(PlaneGeometry)を深度マップに応じてZ方向に
押し出すだけの実装で、見た目が「画像を貼った板が反っているだけ」に近く、
背景も除去されていませんでした。v2では以下の点を作り直しています。

1. **背景の除去**: 画像の四辺から色の類似度をたどるフラッドフィル
   (`segmentForeground`)で被写体シルエットを抽出し、穴埋め・最大連結成分の
   抽出で清書する(`segmentSilhouette`)。背景と判定された領域は
   メッシュそのものを生成しないため、回転させても背景が透けて見えたり
   板状に残ったりしない
2. **本物の立体形状**: 得られたシルエットに対して距離変換
   (`chamferDistanceTransform`)を行い、シルエット境界からの距離を
   丸みのあるプロファイルで厚み(高さ)に変換する(`computeInflationField`)。
   スケッチから3Dモデルを起こすツール(Teddyなど)で使われる
   「風船のように膨らませる」古典的な手法で、輪郭のどの点でも厚みが
   ちょうど0まで滑らかにテーパーするため、前面・背面のサーフェスが
   輪郭上で自然に閉じる
3. **輪郭に沿ったリム(側面)**: メッシュの格子セルのうち「シルエット内の
   セルと外のセルが隣接する辺」だけを`findRimEdges`で拾い、そこに
   前面・背面をつなぐ側面帯を生成する。固定の四角形の外周ではなく、
   被写体の実際のシルエット形状(星形のような凹凸のある輪郭でも)に
   沿ったリムになる

## 重要: 依然としてAIによる3D復元ではありません(ヒューリスティックです)

当初のご指示は「AIによる深度推定」でしたが、実装時点でこのセッションの
ネットワークアクセスがnpm/PyPI等のパッケージレジストリのみに制限されており、
実際の深度推定モデルの重みファイルを配布している`tfhub.dev`・`huggingface.co`
等のホストへアクセスできないという環境上の制約があります
(実際に`@tensorflow-models/depth-estimation`を取得して確認したところ、
npmパッケージ自体はJSコードのみで、モデル本体は実行時に`tfhub.dev`から
取得する仕組みでした)。

v2で「板が反っているだけ」という見た目の問題と「背景が消えない」という
問題は解消していますが、これは**輪郭ベースの幾何学的な推測**であり、
被写体の実際の立体構造をカメラや機械学習で復元しているわけではありません。
特に以下は引き続きヒューリスティックな推測にとどまります。

- 前面から見えない側面・背面の形状(画像に写っていない情報なので、
  当然ながら正確な復元は不可能)
- 被写体の「厚み」自体(輪郭からの距離だけで丸みを推測しており、
  実際の凹凸(例えば服のシワなど)までは反映されない)

「1枚の画像から立体感を推測して、写真を立体物のようにグルグル回して
見られる」という体験を優先し、完全に正確な3Dモデルの生成は目指さない、
という当初のご指示の優先順位に沿った設計です。

## 仕組みメモ

判定・生成ロジックはThree.js描画から独立した純粋関数として`depth.js`に
まとめている(Node上で直接ユニットテスト可能)。

- **背景分離**: `computeAdaptiveThreshold`(背景の色のばらつきから
  閾値を自動調整)→`segmentForeground`(四辺からのフラッドフィル)→
  `fillSmallHoles`→`keepLargestForegroundComponent`→
  `segmentSilhouette`(以上をまとめ、分離に失敗した場合は画面全体を
  被写体とみなすフォールバックつき)
- **立体化**: `chamferDistanceTransform`(シルエット境界からの距離、
  2パスのチャンファー距離変換)→`computeInflationField`
  (0..1に正規化した距離を丸みのあるプロファイルに変換。エッジで
  傾きが無限大になる真の四分円ではなく、有限の傾きを持つ二次関数
  `1-(1-t)^2`を採用し、シルエット輪郭のグリッド量子化ノイズが
  厚みに大きく増幅されないようにしている)
- **メッシュ格子への反映**: `buildGridField`(深度・アルファ場を
  メッシュ格子点にバイリニアサンプリング)→`computeCellInclusion`
  (格子セルの4隅アルファの平均が閾値を超えるセルだけを採用)→
  `buildIndices`(採用セルのみで三角形インデックスを生成、背景セルは
  ジオメトリ自体が存在しない)→`findRimEdges`(採用セルと非採用セルが
  隣接する辺=輪郭線を抽出)
- **境界の完全一致**: 輪郭上の頂点は前面・背面とも厚みを厳密に0へ
  スナップし、リムもZ=0(前面)/Z=-BACK_OFFSET(背面)の平坦な帯として
  生成している。厚みをアルファで減衰させるだけでは輪郭ぎりぎりの頂点に
  わずかな厚みが残ることがあり、そのわずかな段差が真横から見たときの
  ジラジラしたZファイティング(前面・背面・リムが際どく交差して
  ちらつく現象)として現れたため、輪郭頂点だけは明示的に0へスナップして
  段差そのものを無くしている
- 被写体は「前面(実写真テクスチャ)」「背面(元画像を左右反転+ぼかし+
  暗め+彩度低下させたテクスチャ)」「側面リム(輪郭近傍の実画素色を
  頂点カラーとして使用)」の3パーツで構成
  - 背面メッシュはY軸180度回転して配置しているため、前面の格子座標iに
    対応する背面ローカル頂点は**左右反転した列(segments-i)**である
    (そのまま同じ列で対応づけると位置がずれる)。深度サンプリング側で
    あらかじめこの反転を吸収しているため、幾何学的な対応関係の詳細は
    `depth.js`の`buildGridField`(`mirrorU`引数)のコメントを参照
- 解析は128×128に縮小した画像に対して行い、メッシュは88分割
  (89×89頂点)で構築している。実際のテクスチャは長辺1024pxを上限に
  縮小してGPUテクスチャサイズを抑えている

## テスト

- `depth.js`の純粋関数はNode上で直接ユニットテスト済み(合成画像による
  背景分離の精度、チャンファー距離変換、丸みプロファイル、格子への
  反映、輪郭抽出、三角形の巻き順など)
- Playwrightで実際にブラウザ上に画像を読み込ませ、メッシュの三角形数が
  常にグリッド全体より大幅に少ない(=背景が除去されている)ことを検証
- 円・星形など複数の被写体シルエットで見た目を確認し、背景が完全に
  除去されていること、真横から見ても板ではなく丸みのある立体として
  見えることをスクリーンショットで確認
- 背景と被写体の区別がつかない低コントラスト画像でも例外を出さず
  フォールバック(画面全体を被写体とみなす)で描画できることを確認
- 実際の`<input type=file>`経由での読み込み、実ポインタドラッグでの
  回転、リセットボタンの動作を検証
- `window.__debug`フックは最終コミット前に削除済み
