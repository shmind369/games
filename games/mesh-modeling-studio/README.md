# MESH MODELING STUDIO

既存のアニメーション作成アプリ`humanoid-gltf-exporter`で、Tripo
(TripoAI/Tripo Studio)という生成AIサービスで作った3Dモデルに
ボーンを入れてアニメーションを付けられないか、という相談から始まった
プロジェクトです。検証の結果、Tripoで自動リギングした`.glb`を
書き出しても、無料プランでは「スケルトンのエクスポート」自体が
トグルできず(PC・全形式で確認済み)、骨データを持ち出せないことが
分かりました。そこで「モデルにリグを入れる機能を自作できないか」
「完全自動でなく半自動の仕組みならコストはどれくらいか」「初代
バーチャファイター程度のローポリキャラなら簡単か」という一連の
相談を経て、「今作っているアニメーション作成アプリはそのままにして、
別のファイルでモデリング・リギング作成アプリを作ってみたい」という
依頼を受け、新規プロジェクトとして立ち上げました。

**既存の`humanoid-gltf-exporter`には一切変更を加えていません**。
依頼で最も重視されたのが「既存アプリのコードを流用・改変することは
避ける」という点だったため、このプロジェクトは完全に独立したファイル
一式として作成しています(`vendor/`以下のThree.js本体・OrbitControlsは、
このリポジトリの他プロジェクトと同じ第三者ライブラリの同一revision
(r160)をコピーしたものであり、アプリ本体のロジックはすべて新規に
書き下ろしています)。

依頼時に渡された詳細な開発指示書(v0.1)により、今回作るのは
人型専用ではない汎用の3Dモデリング・リギングツールで、開発は
3段階に分けられています。

- **Phase 1(今回実装)**: モデリングの基本構造。頂点(Vertex)・
  辺(Edge)・面(Face)を「頂点を作る→辺を作る→面を作る」の順で
  組み立てられるようにする
- **Phase 2(未着手)**: 任意のボーン数・階層構造を持つ汎用的な
  ボーン(Armature)システム
- **Phase 3(未着手)**: 各頂点を最も近い1本のボーンに100%割り当てる、
  最も単純なスキニング

指示書にある通り、今回はPhase 1のみを実装し、リギング(ボーン・
スキニング)にはまだ着手していません(後述のGLBインポート/
**書き出し**機能はPhase 1の範囲内の追加機能であり、Phase 2/3の
リギングとは別物)。「Blenderのような多機能ソフトを最初から目指
さない」という方針のため、Extrude・Merge・Split・Loop Cut・面の
分割・Mirror・複製などの高度な編集機能も、今回は意図的に実装して
いません。

### 実機テストを受けた操作性の改善

Phase 1の初版をマージした後、実際にスマートフォンで操作して
もらったフィードバックを受け、以下を追加している(いずれもPhase 1の
範囲内の操作性改善であり、Phase 2/3のリギング機能ではない)。

- 既存の頂点を選択してドラッグで移動できること(全ビュー同期)
- TOP/FRONT/LEFTそれぞれが独立したピンチズーム・2本指パンを持つこと
- FREEビューでも直接モデリングできること(タップのみ。ドラッグは
  既存のオービット操作のために空けてある)
- モードがビュー切り替えをまたいで維持されること
- グリッド表示のON/OFF(GRIDボタン)
- グリッドへのスナップ=マグネット機能のON/OFF(MAGNETボタン)

### GLBインポート機能の追加

その後、「Tripoでボーンなしで書き出したGLBモデルを、今のモデリング
アプリで表示できないか」という相談を受けた。単に表示するだけでなく、
「編集可能な頂点/辺/面として取り込みたい(その後このアプリの頂点移動・
将来のリギング機能の対象にしたい)」という方針を確認した上で、GLB
インポート機能(📥 読込ボタン)を追加した。取り込んだ頂点・三角形は、
タップで手作りした頂点・辺・面と完全に同じデータとして扱われる。

### 面カラー機能の追加

続けて、「ローポリゲームモデルにスマートフォン上で簡単に色を付けたい」
という依頼を受けた。テクスチャペイントやPBRマテリアル編集ではなく、
「面を選択→🎨 COLOR→パレットから色を選ぶ→その面がその色になる」
という最小限の操作だけを実装している。将来GLTF/GLBとして書き出す際、
同じ色の面をまとめて1つのMaterialに変換できるよう、各面が直接
Hexカラー文字列を1つ持つだけの単純なデータ構造にしている。

### GLB書き出し機能の追加

続けて、「Tripoで生成したモデルに色を付けて、ゲームに使えるサイズに
してほしい」という依頼を受けた。色付け自体は前述の面カラー機能で
可能だが、結果を実際にゲームへ持ち出すには書き出し(エクスポート)
機能が必要だったため、面カラー機能のデータ構造(Face→Material→
GLTF/GLB)をそのまま実現する形でGLB書き出し機能(📤 書出ボタン)を
追加した。同じ色を持つ面をまとめて1つのMesh/Materialとして書き出す。
これにより、GLBインポート→頂点編集・面カラーリング→GLB書き出し、
という一連の編集サイクルがPhase 1の範囲内で完結するようになった
(リギング・スキニングを伴わない静的なモデルの範囲で)。

### モデル拡大縮小・実寸サイズ表示機能の追加

GLB書き出し機能に続けて、「読み込んだモデルそのものを拡大縮小したい
(カメラのズームではなく、Transform/頂点座標として実際にスケールを
変える)」「現在のオブジェクトの実寸サイズ(X/Y/Z)を画面に表示したい」
という依頼を受けた。➕拡大/➖縮小ボタンでモデル全体のバウンディング
ボックス中心を基準にX/Y/Zを常に同じ倍率でスケーリングし(縦横比・
頂点の相対位置関係を維持)、OBJECTパネルに現在の実寸サイズ(1ワールド
単位=1mとして、m/cm/mmを自動的に使い分ける)と、原寸に対する倍率
(Scale)をリアルタイムに表示する。頂点座標自体を直接書き換える方式の
ため、拡大縮小後も頂点編集・GLB書き出しなど既存の機能はすべてそのまま
正しく動作する。

## 遊び方

`index.html` をブラウザで開くか、ローカルサーバーで配信してください。

```bash
cd games/mesh-modeling-studio
python3 -m http.server 8080
# http://localhost:8080 を開く(スマートフォンでの操作を想定)
```

画面は4分割ビューになっています(指示書で指定されたレイアウト通り)。

```
+--------+--------+
|  TOP   | FRONT  |
+--------+--------+
|  LEFT  |  FREE  |
+--------+--------+
```

- **TOP**: 真上から見た図。タップ/ドラッグはX/Z平面(Yは常に0)に反映
- **FRONT**: 正面から見た図。タップ/ドラッグはX/Y平面(Zは常に0)に反映
- **LEFT**: 左から見た図。タップ/ドラッグはZ/Y平面(Xは常に0)に反映
- **FREE**: 自由視点カメラ。1本指のドラッグは既存のオービット回転
  (従来通り)、ピンチ・2本指ドラッグはズーム・パン(こちらも従来通り)
  に使うため、タップ(ごく小さい移動量・短時間の接触)のときだけ、
  直交3ビューと同じモデリング操作(頂点追加・頂点/辺/面の選択)を行う

モード(頂点/辺/面)は、どのビューをタップしてアクティブビューを
切り替えても維持される(例: 面モードのままTOP→FRONT→LEFT→FREEと
タップしても、ずっと面モードのまま操作できる)。

下部ツールバーでモードを切り替えます。

- **頂点モード**: 何もない場所をタップすると、そのビューの平面上に
  新しい頂点を追加する。既にある頂点をタップすると選択/選択解除、
  選択した状態でドラッグするとそのビューの平面内で移動する
  (選択済みの頂点は、タップ位置が多少ずれていても掴みやすいよう
  広めの当たり判定になる)。FREEビューでは、タップすると3Dカーソルの
  高さに頂点を追加する(詳細は後述)
- **辺モード**: 2つの頂点を順にタップすると、その2点を結ぶ辺を作成する
  (同じ頂点をもう一度タップすると保留を取り消せる)。頂点のない場所の
  辺をタップすると選択/選択解除。どのビューでタップして頂点を選んでも
  構わない(例: TOPで1点目、FREEで2点目をタップして辺を作成できる)
- **面モード**: 3つの頂点を順にタップすると、三角形の面を作成する。
  面の内側をタップすると選択/選択解除

ビュー共通の操作:

- **ピンチ(TOP/FRONT/LEFT)**: 指を広げると拡大、つまむと縮小。
  4つのビューはそれぞれ独立したズーム状態を持つ
- **2本指ドラッグ(TOP/FRONT/LEFT)**: そのビューを平行移動(パン)する
- **GRID**: グリッド表示のON/OFF。3枚のグリッド(TOP用のXZ平面、
  FRONT用のXY平面、LEFT用のZY平面)をまとめて切り替える
- **MAGNET**: ONにすると、頂点の追加・移動がすべて最も近いグリッドの
  格子点にスナップされる(グリッドの格子間隔と完全に一致した単位で
  スナップする)
- **📥 読込**: GLB/glTFファイルを選択すると、そのモデルの頂点・三角形を
  今の頂点/辺/面データに追加で取り込む(既存の頂点/辺/面は消えない)。
  取り込んだ内容全体を1回のUndoでまとめて取り消せる。取り込み後、
  モデル全体が画面に収まるようTOP/FRONT/LEFTのズーム・パンとFREEの
  カメラ位置を自動調整する
- **📤 書出**: 現在の頂点/辺/面(と面カラー)をGLBファイルとして
  書き出し、端末にダウンロードする。同じ色を持つ面はまとめて1つの
  Materialになる。このアプリ自身で書き出したGLBは📥読込でそのまま
  再読み込みでき、色も含めて復元される
- **➖ 縮小 / ➕ 拡大**: モデルがあるときだけ有効。押すたびにモデル
  全体のバウンディングボックス中心を基準に、X/Y/Zへ常に同じ倍率
  (1回あたり×1.2倍/÷1.2倍)をかける。**カメラのズームではなく、
  頂点座標そのものを書き換える実際のスケール変更**なので、画面上で
  モデルの大きさそのものが変わって見える。中心位置・縦横比は保たれる

画面右下(FREEビューの隅)には現在のオブジェクトの実寸サイズを表示する
OBJECTパネルが出る(モデルがあるときだけ)。

```
OBJECT
Size
X 0.85 m
Y 1.72 m
Z 0.42 m

Scale
1.00
```

バウンディングボックスのX/Y/Zの大きさを、1ワールド単位=1mとして
m/cm/mm(0.01m未満はmm、1m未満はcm、それ以外はm)で見やすく表示する。
拡大縮小すると実寸サイズ・Scaleともにリアルタイムで更新され、
「元に戻す」をすると拡大縮小前の値に戻る。

共通の操作:

- **🗑 削除**: 現在のモードで選択中の頂点/辺/面を削除する(頂点を
  削除すると、それを参照している辺・面も連鎖的に削除される)
- **↩ 元に戻す**: 直前の変更(追加・移動・削除・色変更)を1つ取り消す
- **🎨 COLOR**: 面モードで面を1つ選択しているときだけ有効になる。
  押すとカラーパレットが開き、肌色・白・黒・赤・青・緑・黄・
  オレンジ・紫・グレーの基本10色、または自由な色(カラーピッカー)
  から選ぶと、選択中の面がその色になりパレットが閉じる。色を
  変更しても選択状態はそのまま維持される(選択中は既存の選択
  ハイライト(黄)が優先表示されるため、実際の色は選択を解除すると
  確認できる)

## 仕組みメモ

### データモデル(Three.js非依存)

指示書にある通り、将来GLB/glTFへ書き出すことやPhase 2/3でのボーン・
スキニング追加を見据え、データを素のJavaScriptオブジェクト(Three.js
のジオメトリやメッシュに依存しない形)で保持している。

```js
vertices = [{ id, x, y, z }];
edges    = [{ id, a, b }];        // a, bは頂点id
faces    = [{ id, verts: [a,b,c], color }]; // colorは未設定ならnull
```

描画(`rebuildScene`)は、このデータが変化するたびに`Three.js`の
`Mesh`/`LineSegments`を作り直すだけの単純な構成。頂点数十〜数百程度の
このプロトタイプの規模では、差分更新をせず毎回全体を再構築しても
十分な速度が出る。

### 4分割ビューと、同じシーンへの4回描画

`third-person-boxer-3d`等とは独立に、このプロジェクト用に新しく
実装した。1枚の`<canvas>`に対して`renderer.setScissorTest(true)`を
有効にし、4つの矩形それぞれに`setViewport`/`setScissor`を設定して
同じ`scene`を4回(TOP→FRONT→LEFT→FREEの順に)`render()`するだけで、
4分割ビューを実現している。直交3ビュー用カメラ(`OrthographicCamera`)
は`up`ベクトルと向きだけを変え、FREEビュー用に`PerspectiveCamera`+
`OrbitControls`を1つ用意している。

### タップ位置→3D座標への変換

直交ビューごとに固定した平面(TOP: Y=0平面、FRONT: Z=0平面、
LEFT: X=0平面)を用意し、タップ位置からその平面への
`Raycaster`との交点を求めることで3D座標を決定している
(`humanoid-gltf-exporter`の3Dカーソル機能と考え方は同じだが、この
プロジェクト用に独立して実装したコード)。パン・ズームはカメラの
位置・画角を変えるだけで、この平面自体は動かさないため、追加の
補正なしでそのまま成立する。

### 3Dカーソル(FREEビューでの頂点追加の奥行き決定)

FREEビューでのタップは画面上の1点しか与えないため、3軸のうち
どれか(実装上はY、すなわち高さ)が決まらない。そこで「最後に
作成・選択・移動した頂点の位置」を3Dカーソル(マゼンタ色の
八面体で常時表示)として保持し、FREEビューでの新規頂点追加は、
このカーソルのY座標を通る水平面との交点として配置する
(`pointOnFreeViewCursorPlane`)。どのビューで頂点を触っても
カーソルは追従するため、「TOP/FRONT/LEFTで狙った高さに頂点を
選択・移動してから、FREEビューでその高さを基準に次の頂点を
置いていく」という一貫した使い方ができる。

### 当たり判定

頂点・辺・面とも、3D座標をそのビューのカメラで画面座標に投影してから、
画面上の距離で判定している(スクリーン空間ベース)。

- 頂点: 投影点との距離が24px以内で最も近いものを選ぶ(既に選択中の
  頂点は、さらに広い38px以内なら多少タップ位置がずれていても掴める)
- 辺: 2頂点の投影点を結ぶ線分との距離(点と線分の最短距離)が16px以内
- 面: 3頂点の投影点が作る三角形の内部にタップ位置が入っているか
  (符号付き面積を使った内外判定)

タップ(`DRAG_THRESHOLD_PX`=8px未満の移動かつ500ms未満の接触)と
ドラッグは、`pointerdown`時の座標・時刻と`pointerup`時の座標・時刻の
差で区別している。

### グリッド(3枚の実座標系グリッド)

TOP/FRONT/LEFTそれぞれの基準面に対応したグリッドを、実際に3D空間上に
存在する3枚の`GridHelper`として用意している。標準の`GridHelper`は
XZ平面(Y=0)に配置されるため、TOP用はそのまま、FRONT用はX軸周りに
90度、LEFT用はZ軸周りに90度回転させることで、それぞれXY平面(Z=0)・
ZY平面(X=0)のグリッドを作っている。3枚とも実体のある3Dオブジェクト
なので、FREEビューではどの角度から見ても立体的に正しく見え、直交
ビューでもそれぞれの基準面に対応した2D格子として正しく見える
(GRIDボタンで3枚まとめてON/OFFする)。

グリッドの格子間隔(`GRID_SIZE / GRID_DIVISIONS` = 6/12 = 0.5)は、
下記のマグネット機能のスナップ単位と完全に同じ値を使っている。
これにより「グリッドが見えている間隔」と「実際にスナップされる
間隔」が常に一致する。

### マグネット(グリッドスナップ)

MAGNETボタンでON/OFFを切り替える。ONのときは、頂点の新規追加・
ドラッグ移動のどちらでも、計算済みの3D座標(直交ビューなら
`pointOnViewPlane`、FREEビューなら後述の3Dカーソル平面との交点)の
X/Y/Z各成分を、スナップ単位の倍数に丸める(`snapPoint`)。直交
ビュー・FREEビューのどちらでも同じ関数を通すため、挙動は4ビューで
統一されている。

### FREEビューとOrbitControlsの切り替え・共存

直交3ビューをドラッグしている間、同じポインター操作で`OrbitControls`
(FREEビューのカメラを動かす)が反応してしまわないよう、`pointerdown`
のcaptureフェーズで、新しいジェスチャー列の最初の指が触れた瞬間に
タップされたビューを判定し、`free`以外ならその場で
`controls.enabled = false`にする(2本目以降の指が別のビューに
触れても、進行中のジェスチャーの対象ビューは変えない)。

FREEビューでは`controls.enabled = true`のまま(=既存のオービット・
ズーム・パン操作は常に生きている)にしつつ、それとは別に「タップ
(移動量8px未満・接触時間500ms未満)」だけを`pointerup`時に検出して
モデリング操作(頂点追加・頂点/辺/面の選択)を行う。オービット用の
ドラッグとモデリング用のタップは同じ指の同じジェスチャーの中で
共存しており、OrbitControls側は小さな動き(タップ)にはほぼ反応
しないため、互いに干渉しない。

### ピンチズーム・2本指パン(TOP/FRONT/LEFT)

2本の指が同じ直交ビューの矩形内に入った時点で、そのビュー専用の
ピンチ/パンジェスチャーを開始する(進行中だった1本指の頂点ドラッグ
などは打ち切る)。各ビューは`{ zoom, panX/panY/panZ(該当する2軸分) }`
という独立した状態を持ち、`updateOrthoCameraTransform`で
正投影カメラの視錐台(ズームに応じた半幅・半高)とカメラの位置/
注視点(パンに応じたオフセット)を毎回再計算する。

ズームとパンは「指の間の中点の真下にある3D空間上の点が、指の動きに
合わせて画面上の同じ位置に留まり続ける」という1つの考え方
(`applyPinchPan`)で同時に処理している。具体的には、ズーム変更の
前後でその中点に対応するワールド座標を`pointOnViewPlane`で求め、
その差分をパンに加算する。これにより、ピンチ(指の間隔の変化)も
2本指ドラッグ(指の間隔を保ったままの平行移動)も、同じコードで
自然に扱える。3本目以降の指は無視する。

直交ビューの編集平面(例: TOPならY=0平面)自体はパン・ズームで
動かないため、`pointOnViewPlane`によるタップ→3D座標変換は、カメラが
どれだけパン・ズームしていても追加の補正なしでそのまま正しく動作する。

### GLBインポート(編集可能な頂点/辺/面への変換)

`vendor/loaders/GLTFLoader.js`・`vendor/utils/BufferGeometryUtils.js`は、
`third-person-boxer-3d`と同じThree.js本家(r160)の第三者ライブラリを
そのままコピーしたもの(アプリ本体のロジックではない)。GLTFLoaderの
`parse()`でファイルの中身(ArrayBuffer)を直接解析し、サーバーやネット
ワークを経由せず端末内だけで完結する。

GLTFの頂点バッファは、法線やUVが異なるだけで同じ座標に複数の頂点
エントリを持つことが多い(フラットシェーディング等のため)。そのままでは
隣接する三角形が別々の頂点を参照してしまい、「頂点を動かすと隣の面も
一緒に動く」という編集可能なトポロジーにならない。そこで座標を
量子化したキー(`IMPORT_WELD_EPSILON`=0.0001単位)でほぼ同じ位置の
頂点をまとめる「溶接」を行い、同じ位置は必ず同じ頂点idになるようにして
から、面(`addFace`)・辺(`addEdge`)を作成している(既存の重複防止
ロジックをそのまま利用)。マグネット(グリッドスナップ)は、インポート
した座標には適用しない(元モデルの形状をそのまま保つため)。

溶接マップ(`vertexIdByKey`)は、GLB内に複数のMeshが含まれる場合も
ファイル全体で1つを共有する。これは、後述のGLB書き出しが面カラー
ごとに別々のMesh(頂点バッファ)として書き出すため、色の境界をまたぐ
頂点をMesh単位で溶接すると重複してしまうことに対応するため(この
アプリ自身が書き出したGLBを再読込した際、色の境界であっても1つの
編集可能な頂点として正しくまとまる)。

マテリアルがテクスチャ(`material.map`)を持たない単純な単色マテリアル
の場合は、その色をそのまま面の`color`として引き継ぐ。これにより、
このアプリ自身が書き出したGLB(面ごとに単色マテリアル)を再読込すると、
面カラーも含めて完全に復元される。テクスチャ付きのマテリアル(Tripo
などAI生成モデルの多くが該当)は、UV・テクスチャ自体を保持しない
既存方針のまま対象外とする(詳細は後述)。

インポート全体は`pushUndoSnapshot()`を1回だけ呼んでから一括で頂点・
辺・面を追加する(頂点1個ごとにUndoを積むと、数百頂点のモデルで
スタックが埋まってしまうため)。取り込み後は、追加された全頂点の
バウンディングボックスを計算し、TOP/FRONT/LEFTそれぞれのズーム・パンと
FREEビューのオービット距離・注視点・3Dカーソル位置を、モデル全体が
ちょうど収まるサイズに自動調整する(`fitViewsToBounds`)。

### 頂点の描画(Points化によるスケーラビリティ)

当初は頂点ごとに個別の`THREE.Mesh`(球)を1つずつ生成していたが、
GLBインポートで頂点数が数百〜1000個規模になり得るため、4分割ビュー×
数百Meshの描画コストが無視できなくなる。そこで全頂点をまとめて1つの
`THREE.Points`で描画する方式に変更した(描画呼び出しは常に1回)。
`sizeAttenuation: false`にすることで、点のサイズはズーム・カメラ距離に
関わらず常に一定のピクセルサイズになり、どのビュー・どのズーム倍率でも
タップしやすい見た目を保てる。選択中/選択途中の頂点は点の色を変えて
見分けている。辺(`LineSegments`)・面(`Mesh`)はもともと全体をまとめた
単一のジオメトリとして再構築していたため、この点では変更していない。

### GLB書き出し(面カラーをMaterialへ変換)

`vendor/exporters/GLTFExporter.js`は、`humanoid-gltf-exporter`と同じ
Three.js本家(r160)のGLTFExporterをそのままコピーしたもの
(`vendor/utils/TextureUtils.js`はその内部依存で、こちらも同様に
第三者ライブラリをコピーしただけ)。

書き出し処理(`buildExportScene`)は、面を`color`(未設定ならデフォルト
の緑)でグループ化し、同じ色を持つ面だけをまとめた1つの
`BufferGeometry`+`MeshStandardMaterial`(`roughness:1, metalness:0`の
フラットな質感)を色の種類の数だけ作る。これにより「面カラー機能」の
データ構造(Face→Material→GLTF/GLB)がそのまま実現できる。
`GLTFExporter.parse(scene, onDone, onError, { binary: true })`で
glTFバイナリ(.glb)のArrayBufferを得て、`Blob`+`<a download>`で
端末にダウンロードさせている。

色の境界をまたぐ頂点は、色ごとに別々の頂点バッファへ複製される
(マテリアル境界での「縫い目」は3DCGでは一般的な挙動)。これ自体は
見た目に影響しないが、再インポート時に正しく1つの頂点として扱える
よう、前述の通りインポート側の溶接マップをファイル全体で共有する
ことで対応している。

### モデルの拡大縮小(頂点座標への直接反映)

「カメラのズーム機能ではなく、Transform/Scale自体を変更してほしい」
という要件のため、ビューのズーム(`viewTransform`、カメラの画角だけを
変える)とは完全に別の仕組みとして実装した。`scaleModel(factor)`は、
モデル全体のバウンディングボックス中心を求め、各頂点を
`center + (v - center) * factor`で置き換える。X/Y/Zに同じ`factor`を
使うため縦横比は保たれ、中心からの線形スケールなので頂点同士の
相対的な位置関係も自動的に保たれる。

頂点座標そのものを書き換えるだけで、Three.jsの`Object3D.scale`の
ような別のTransformノードは使っていない。これにより、当たり判定・
ドラッグ編集・GLB書き出しなど、頂点座標を直接参照している既存の
すべての機能が、追加のコード変更なしでそのまま正しく動作する
(GLBへ書き出す際も、実際にスケール後の頂点座標がそのまま出力される)。

表示用の`modelScale`(原寸に対する倍率。初期値1)は、頂点データとは
別に保持し、Undoのスナップショットにも含めている。カメラズームとは
無関係な値であることを明確にするため、ボタンを押すたびに
`modelScale *= factor`で更新するだけの単純な仕組みにしている。

ビューの自動フィット(`fitViewsToBounds`、GLBインポート時に使用)は、
拡大縮小のボタン操作では意図的に呼び出していない。呼び出すとカメラが
毎回ちょうど良く再ズームしてしまい、「モデルが実際に大きくなった」
ことが画面上で分かりにくくなるため。

### オブジェクトサイズ表示

`updateObjectInfo`は、`rebuildScene`(データが変化するたびに必ず
呼ばれる関数)の最後で毎回呼び出される。モデル全体のバウンディング
ボックスの大きさ(X/Y/Z)を求め、1ワールド単位=1mという前提のもと
`formatLength`で見やすい単位(1m以上はm、1m未満0.01m以上はcm、
それ未満はmm)に変換して表示する。拡大縮小・頂点移動・Undo・GLB
インポートなど、頂点座標を変化させるすべての操作の後に自動的に
最新の値へ更新される(`rebuildScene`経由で呼ばれるため、個々の
操作ごとに表示更新のコードを追加する必要がない)。

### ビューの自動フィットにあった不具合の修正

今回の拡大縮小機能のテスト中に、`fitViewsToBounds`(GLBインポート時や
テストから呼び出す自動フィット)が、ビューの矩形が正方形でない場合
(スマートフォンでは縦長/横長になるのが普通)に、片方の軸だけで
ズーム倍率を決めてしまい、もう片方の軸がわずかにビューからはみ出す
ことがある不具合を発見し、修正した。横方向に必要な半幅と縦方向に
必要な半高さをそれぞれ独立に求め、矩形のアスペクト比で正しく
割り戻してから大きい方を採用するよう`fitZoom`を書き直している。
GLBインポート機能自体のPR時点から存在していた不具合で、モデルの形状と
ビューの矩形比率の組み合わせによっては発生しない場合もあったため、
今回のテストで初めて顕在化した。

### Undo(全体スナップショット方式)

このプロトタイプの規模(頂点・辺・面とも数十〜数百程度を想定)では、
変更の都度`vertices`/`edges`/`faces`全体を複製してスタックに積む
だけの単純な方式で十分な性能が出るため、個別の差分管理はしていない
(最大50件まで保持)。頂点のドラッグ移動も、ドラッグ開始時の
スナップショットを`pointerup`時にまとめて1件だけ積むことで、
ドラッグ中の細かい移動すべてがUndo1回分にまとまるようにしている。

### 面カラー(簡易カラーリング)

各面(`face`)が`color`(例: `"#E0483E"`、未設定なら`null`)を1つだけ
直接持つ、最も単純なデータ構造にしている。`cloneState`/`restoreState`
(Undoのスナップショット)にも`color`を含めているため、色変更も既存の
Undoの仕組みにそのまま乗る(`setFaceColor`を呼ぶ前に`pushUndoSnapshot`を
1回呼ぶだけで、他の変更と全く同じ扱いになる)。

描画(`rebuildScene`)側は、既存の「選択中の面は黄色、それ以外は緑色」
という分岐の「それ以外」の色を`f.color`(未設定ならデフォルトの緑)に
差し替えただけ。面は元々、頂点ごとではなく面ごとに1色をまとめて
3頂点分プッシュする構造になっていたため、変更はこの1行で済んでいる。
選択中は引き続き黄色のハイライトを優先表示する(「今どの面を選択して
いるか」を常にひと目で分かるようにするため、色を選んでも選択表示を
上書きしない方針)。選択はタップ操作やUndoでのみ変化するため、色を
変更しても`selectedFaceId`自体は変化せず、選択状態は自然に維持される。

カラーパレットは`<div id="colorPaletteOverlay">`という、通常時は
`display:none`の全画面オーバーレイ(背景タップでも閉じる)。基本10色の
スウォッチボタンと、`<input type="color">`(端末標準のカラーピッカー)を
用意しており、どちらを選んでも同じ`applyColorToSelectedFace`関数を
通る。カラーピッカーは`input`(ドラッグ中に連続発火)ではなく`change`
(確定時に1回だけ発火)を購読することで、ドラッグ中に大量のUndo
スナップショットが積まれないようにしている。

将来GLTF/GLBとして書き出す際は、同じ`color`を持つ面をまとめて1つの
`Material`に変換し、`materials`配列と各`primitive`の`material`
インデックスを割り当てる、という変換が素直に書ける設計にしている
(Face→Material→GLTF/GLBという指示書の拡張方針に沿う)。

## 今後について

指示書の通り、Phase 1が安定したことを確認できたので、次のPhase 2
(任意のボーン数・階層構造を持つ汎用ボーンシステム)、Phase 3
(各頂点を最も近い1本のボーンへ100%割り当てる最単純なスキニング)は、
別途依頼を受けてから着手する。Phase 1の範囲内でも、以下は今回は
意図的に実装していない(指示書で「最初から目指さない」とされている
範囲、または将来の拡張として位置付けられている範囲)。

- オブジェクト全体の移動・回転(個々の頂点の移動と、拡大縮小のみ対応)
- Extrude・Merge・Split・Loop Cut・面の分割・Mirror・複製
- 四角形以上の面(GLBインポート・手作りとも三角形のみ対応。GLB側が

  を取り込む)
- インポートしたモデルの法線・UV・マテリアル・テクスチャの保持
  (頂点座標と三角形の接続関係だけを取り込み、見た目は単色の面として

- ズーム量に応じたグリッド間隔・表示密度の自動調整(現状は常に
  固定間隔。要望では「してもよい(任意)」とされている範囲)
- FREEビューでの頂点のドラッグ移動(タップのみ対応。ドラッグは
  既存のオービット操作のために空けてあり、今回は意図的に対象外と
  している)
- テクスチャペイント・UV編集・PBR(金属度/粗さ等)・複雑なマテリアル
  編集・高度なシェーダー(指示書で明示的に範囲外とされている)
- 複数の面をまとめて選択し、一括で色を変更する機能(現状は単一選択の
  みのため未実装。複数選択機能自体が将来追加された場合は、同じ
  `applyColorToSelectedFace`の仕組みを選択中の全面に適用するだけで
  拡張できる)
- 色のリセット(未設定に戻す)専用ボタン(Undoで同等のことができるため
  今回は見送り)
- GLB書き出し時のテクスチャ・UV・リギング情報の付与(今回は面ごとの

  元のテクスチャを保ったままの書き出しは対象外)
- モデルの個別軸(X/Y/Zだけを別倍率で)の拡大縮小(常にX/Y/Z同倍率の

- 拡大縮小量を数値で直接入力する機能(➕/➖ボタンによる1.2倍/÷1.2倍の
  段階的な変更のみ対応)
